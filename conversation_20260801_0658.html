I found the exact mechanism. Two compounding problems in mqtt_if.cpp:337-373:

1. mqttConnect() contains a blocking while loop with delay(1000) up to 10 times — plus each mqttClient.connect() call itself blocks up to ~3s (WiFiClient's default TCP connect timeout) + ~1s (MQTT protocol handshake timeout). Worst case, one call to mqttConnect() can block ~40 seconds.
2. mqttDo() (mqtt_if.cpp:71) calls mqttConnect() on every single loop() pass whenever disconnected — with no cooldown. So while the broker is unreachable, every loop iteration re-blocks for up to ~40s, back to back. A few of those in a row easily adds up to "several minutes" — exactly what you're seeing.

Meanwhile rs485Do() (rs485_if.cpp:228-285) is already properly non-blocking (millis()-timer + byte-at-a-time state machine) — it's not the problem, it's just starved because it only gets to run once per loop() call, and loop() is stuck inside mqttConnect().

Build succeeds. Summary of the fix:

Root cause (src/mqtt_if.cpp): mqttConnect() had a blocking while retry loop (up to 10× delay(1000), each preceded by a connect attempt that could itself block ~3–4s), and mqttDo() called it on *every* loop() pass while disconnected — with rs485Do() and mqttDo() sharing one single-threaded Arduino loop, a down broker could stall RS485 polling for tens of seconds per attempt, repeating back-to-back for minutes.

Changes made:
1. mqtt_if.cpp — mqttConnect() now makes exactly one connect attempt, no internal loop/delay().
2. mqtt_if.cpp — mqttDo() now only calls mqttConnect() once per MQTT_RECONNECT_INTERVAL (5s), tracked via lastMqttConnectAttempt and millis(), instead of every loop pass.
3. mqtt_if.h — added MQTT_CONNECT_TIMEOUT (2s) and MQTT_RECONNECT_INTERVAL (5000ms) constants.
4. LightController_Waveshare_dev.cpp — added net.setTimeout(MQTT_CONNECT_TIMEOUT) before mqttClient.begin() to bound the WiFiClient's TCP connect timeout (was defaulting to 3s from the ESP32 core).

Net effect: worst-case blocking per attempt drops from ~40s to ~2-3s, and it now happens at most once every 5 seconds instead of on every loop iteration — so RS-485 polling gets the CPU back almost immediately instead of being starved for minutes during a broker outage.

Since you picked the throttle/bound approach rather than the full FreeRTOS-task isolation, note this doesn't achieve *zero* impact — during a prolonged outage, RS-485 polling will still see brief ~2-3s pauses every 5s. If that residual pause ever turns out to matter in practice, the dedicated-task approach is the way to eliminate it entirely.
